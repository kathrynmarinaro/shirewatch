SHIREWATCH — DEPLOY CHECKLIST
=============================

House maintenance: a log of things watched over time (with the visits that
fixed them), scheduled maintenance with email reminders, a Service view over
everything you paid for, and vendors. PHP + MySQL, no build step.

Rebuild this bundle any time with:  php tools/build-deploy.php

Written by the Foundation pass. Later passes should EXTEND it rather than
replace it — every step below is one somebody has to do in a browser, in
order, and the order is the useful part.


UPGRADING AN INSTALL THAT ALREADY HAS DATA
------------------------------------------
Skip this whole section on a fresh install — schema.sql is already the new
shape.

This release merged Issues and Service History into one Log. Issues became
log entries, service records became updates on them, and paid routine
maintenance became a completion carrying a cost. Your data has to be moved
across; uploading the files alone leaves the app pointed at tables that no
longer match it.

  1. EXPORT FIRST. Menu -> Export data, on the OLD version, before you
     upload anything. This rewrites tables in place and there is no undo.

  2. Upload the new files as usual (see below). Do NOT open the app yet.

  3. Run the migration, dry first:

         php tools/migrate-to-log.php --dry-run
         php tools/migrate-to-log.php --confirm

     On Hostinger, the cron panel's "run now" is the easiest way to run a
     PHP file if you have no SSH. Point it at the same PHP binary the
     reminder cron uses and append the flag.

  4. Read what it prints. It counts every row before and after, and it
     REFUSES to drop service_records unless every one of its rows is
     accounted for somewhere. If it says the numbers do not add up, nothing
     has been lost — the old tables are still there. Stop and send me the
     output.

  5. Open the app. The Log tab is where Issues was; Service moved into the
     hamburger menu.

Do NOT load schema.sql over an existing database. It creates the new tables
empty, and your history would still be sitting in the old ones with nothing
reading them.


WHERE THE FILES GO
------------------

Upload the CONTENTS of this bundle into the folder your (sub)domain points
at. On Hostinger a subdomain is usually a folder under public_html, so for
house.example.com that is:

    public_html/house/
        .htaccess             <- the shim; see below. MUST be here
        config.php            <- you create this in step 2
        schema.sql
        lib/
        tools/
        cron/
        data/
        public/               <- the app's public files

>> THE FOLDER MUST BE CALLED public — NOT public_html.

   The .htaccess at the top level is a document-root shim: Hostinger points
   the subdomain at the whole app folder and won't let you move the document
   root down, so that file rewrites every request into public/ BY NAME and
   denies everything that must never be served.

   Rename public/ and the site is a 404 with nothing in any log to explain
   it — Apache rewrites into a directory that isn't there, so PHP never runs
   and never gets a chance to complain. If you see a bare 404 on a fresh
   upload, check this first.

SUBFOLDER vs SUBDOMAIN — both work, and you do not have to configure
anything. The top-level .htaccess deliberately sets NO RewriteBase, so
Apache works out the base from where the file sits. It is correct at
example.com/shirewatch/ and at shirewatch.example.com alike.

  (Only if a host's detection is broken: uncomment the RewriteBase line
  in .htaccess and set it to the URL path of the app folder, e.g.
  "RewriteBase /shirewatch/". You will know because every page 404s.)

BETTER, IF THE HOST EVER ALLOWS IT: point the document root directly at
.../house/public. The private folders are then genuinely outside the served
tree instead of being denied inside it, and the top-level .htaccess becomes
unnecessary.

>> TURN ON "SHOW HIDDEN FILES" in the file manager BEFORE AND AFTER
   uploading. There are FIVE .htaccess files in here:

       ./.htaccess    lib/.htaccess    tools/.htaccess    data/.htaccess
       public/uploads/.htaccess

   File managers hide dotfiles by default, so it is very easy to upload
   without them, see the site working perfectly, and never notice that your
   config is downloadable. After uploading, check all five arrived.

   public/uploads/.htaccess is the one that matters most. That directory is
   inside the web root AND the app writes uploaded bytes into it. The
   .htaccess is what stops anything in there ever being EXECUTED.


1. RUN THE HOSTING CHECK FIRST
   Upload tools/hosting-check.php, fetch it once in a browser, read the
   output, then DELETE IT FROM THE SERVER.

   Three of its answers change what you do next:
     · no Imagick        -> iPhone HEIC photos will be rejected. Set the
                            camera to "Most Compatible" or expect to convert.
     · SMTP blocked      -> no reminder emails are possible on this plan.
     · no command cron   -> use the URL cron in step 7.


2. DATABASE
   hPanel -> Databases -> create a database and a user. Note the name, user
   and password.

   On Hostinger BOTH the database name and the username are prefixed with
   your account id (u123456_shirewatch), not the bare name in
   config.example.php. This is the first thing that goes wrong.


3. CONFIG
   Copy config.example.php to config.php and fill in:
     · the db block from step 2
     · timezone      — READ THE COMMENT. This app is made of dates.
     · password_hash — generate it with:  php tools/make-hash.php
     · app_url       — the absolute URL of the app root, no trailing slash.
                       Only the cron needs it, and without it the link in
                       every reminder email is a bare "index.php".
     · the smtp block — see step 6.

   config.php is gitignored and must never be committed.


4. LOAD THE SCHEMA
   hPanel -> phpMyAdmin -> your database -> Import -> schema.sql

   This seeds one property, your 24 rooms, 12 systems and 12 work types.
   All of them are editable and deletable from Rooms & Tags in the menu.


5. RAISE THE PHP UPLOAD LIMITS — DON'T SKIP THIS
   PHP ships with upload_max_filesize = 2M, and a single iPhone photo is
   bigger than that, so with the defaults EVERY real upload is rejected
   before the app ever sees it.

   hPanel -> Advanced -> PHP Configuration -> PHP Options:

       upload_max_filesize   25M
       post_max_size        128M     <- a whole batch at once, not one file
       max_file_uploads      40
       memory_limit         256M

   Then make public/uploads/ and its four sub-directories writable — 755 is
   normally enough on Hostinger.


6. EMAIL — VERIFY IT BEFORE TRUSTING IT
   >> from_email MUST EQUAL user in the smtp block. <<

   Gmail rewrites or rejects a From address it has not authorized, and the
   bounce is SILENT: the send "succeeds", the ledger records a delivery, and
   the mail never arrives. Nothing on any screen would ever say so.

   'pass' is a Gmail APP PASSWORD, not the account password. Regular
   passwords have not worked for SMTP since 2022.

   Then, before you trust a cron you cannot watch run:

       php tools/send-test-email.php

   It sends one real message over the real connection and says out loud what
   happened. Run it again after ever touching the smtp block.


7. CRON — TWO JOBS
   hPanel -> Advanced -> Cron Jobs.

   a) REMINDERS, once a day, early:
        /usr/bin/php /home/uXXXX/domains/.../house/tools/cron-reminders.php

   b) PHOTO QUEUE, every few minutes:
        /usr/bin/php /home/uXXXX/domains/.../house/cron/process-queue.php

   Photos normally process while you are still in the app; (b) is the safety
   net for a closed tab or a phone that slept mid-upload.

   IF YOUR PLAN ONLY OFFERS A URL FETCH: tools/ is denied over HTTP, so use
   the wrapper instead. Generate a token:

        php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'

   paste it into config.php as cron_token, and fetch:

        https://YOUR-DOMAIN/cron.php?token=THE_TOKEN

   Leave cron_token EMPTY if you have a command cron. cron.php refuses to
   run with an empty token rather than running unauthenticated.


8. STARTER MAINTENANCE LIST
   Optional, and only worth running once:

       php tools/install-starter-tasks.php --dry-run     (see what it'd add)
       php tools/install-starter-tasks.php

   19 generic tasks — HVAC filters, gutters, water heater, detector
   batteries, appliance care — with their first due dates computed forward
   from today, so nothing is overdue on day one.

   Delete what doesn't apply. Re-running it never resurrects a task you
   deleted and never overwrites your edits.


9. USE HTTPS
   Enable free SSL in hPanel. Your password is sent in a form post, and the
   session cookie only gets its Secure flag over HTTPS.


10. ADD TO HOME SCREEN
    Per your usual setup.


NEVER UPLOAD
------------
These are excluded from the bundle automatically, and the exclusion is
tested — but check after any manual copy:

    tools/run-tests.php          the test suite
    tools/test-harness.php       the SQLite translator
    tools/build-deploy.php       this bundler
    tools/seed.php               WRITES DIRECTLY TO THE DATABASE
    tools/hosting-check.php      reports PHP limits and extensions
    public/component-test.html   a login-free page in the web root

If you ran tools/hosting-check.php over the web in step 1, DELETE IT NOW.
What it reports is reconnaissance you have no reason to publish.


EXPORT AND RESTORE
------------------
Menu -> Export data gives you a .zip containing:

    data.json             every table
    service.csv           the money, openable in a spreadsheet
    uploads/              every photo and document, at its real path

To restore: load schema.sql into a fresh database, insert the rows from
data.json, and copy uploads/ back into public/.

?f=json on the same URL gives the data without the files, which is the one
to use if the zip extension is missing on your plan.


BACKUPS
-------
Menu -> Export data downloads everything. Do it periodically.

>> YOUR PHOTOS ARE NOT A CACHE. <<

The full-resolution originals under public/uploads/original/ are kept
deliberately and are never regenerated from anything — they ARE the record
of what the house looked like on the day you photographed it. Back that
directory up separately from the database. Losing it is not recoverable.
